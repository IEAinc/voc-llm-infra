# VOC LLM 운영 가이드

중계 서버(EC2)와 추론 서버(RunPod)를 운영하는 사람을 위한 문서입니다. 배포, 일시정지, 상태 확인, 장애 대응 방법을 정리했습니다.
설계 배경은 [aws-설계.md](../aws-설계.md)와 [runpod-설계.md](../runpod-설계.md)를 참고하세요.

## 1. 구성 한눈에 보기

```
고객사 VOC 서버 ──HTTPS──▶ EC2 중계 서버 (voc-llm-gateway, 서울)
                            │  nginx: 고객사 키 확인, 업무시간 외 503
                            │  평일 08:30 자동으로 켜지고 18:10 스스로 꺼짐
                            │  cron: 부팅 시 Pod 기동, 업무시간 2분 간격 감시, 18:00 Pod 종료
                            └──HTTPS──▶ RunPod GPU Pod (vLLM, 업무시간에만 존재)
```

| 항목 | 값 |
|---|---|
| API 주소 | `https://43-200-20-252.sslip.io/v1/chat/completions` (임시 도메인. 실제 도메인이 정해지면 바뀝니다) |
| 모델 이름 | `voc-llm` (실제 모델은 `GET /v1/models` 응답의 `root`에서 확인) |
| EC2 | `voc-llm-gateway` (`i-0690b13503d7390c9`), 고정 IP `43.200.20.252` |
| 서버 경로 | 설정 `/opt/voc-llm/.env`, 스크립트 `/opt/voc-llm/bin/`, 로그 `/var/log/voc-llm/pod.log` |

비용은 대부분 RunPod에서 나옵니다(GPU 시간당 약 $0.59). EC2도 평일 08:30~18:10에만 켜집니다. 꺼져 있는 시간(평일 밤, 주말)에는 API가 응답하지 않고 연결 타임아웃이 납니다.

## 2. 자동 일정 (평일, 한국 시간)

| 시각 | 동작 |
|---|---|
| 08:30 | EC2 시작 (AWS EventBridge Scheduler `voc-llm-ec2-start`). 공휴일에도 켜집니다 |
| 부팅 직후 (약 08:31) | Pod 기동 (공휴일, 일시정지 중이면 건너뜀), 밤사이 꺼 둔 알람과 외부 접속 감시 다시 켬 |
| 월요일 08:40 | 공휴일 목록 갱신 |
| 09:00~17:58, 2분 간격 | Pod 상태 감시와 자동 복구 (공휴일, 일시정지, 점검 모드 중이면 건너뜀) |
| 18:00 | Pod 종료 (일시정지 중에도 항상 실행) |
| 18:10 | 알람과 외부 접속 감시를 끄고 EC2 종료. **Pod 삭제에 실패했으면 EC2를 끄지 않고** "EC2 shutdown skipped" 메일을 보냅니다 |
| 19:30 | 18:10에 꺼지지 않았을 때 Pod 삭제와 EC2 종료를 한 번 더 시도 |

- EC2 시작 스케줄은 AWS 콘솔 → Amazon EventBridge → 스케줄러 → 일정에서 확인하고 끌 수 있습니다.
- 18:10 종료는 업무시간(평일 08:30~18:00)에는 동작하지 않습니다. 주말이나 밤에 EC2를 직접 켰다면, 다 쓰고 나서 `sudo /opt/voc-llm/bin/voc-ctl.sh shutdown`으로 꺼 주세요. 끄지 않으면 다음 18:10까지 켜져 있습니다.

### 수동 모드 (주말·야간 작업)

관리자 PC에서 실행합니다. `infra/aws.env`, `infra/aws.out`, `infra/voc-llm-key.pem`이 필요하고, PC의 IP가 보안그룹 22번에 허용되어 있어야 합니다.

| 명령 | 동작 |
|---|---|
| `bash infra/manual-on.sh` | EC2가 꺼져 있으면 켜고 Pod를 띄웁니다. 18:00 Pod 종료와 18:10/19:30 EC2 종료를 건너뜁니다. 건너뛸 때마다 "Auto shutdown skipped (manual mode)" 메일이 갑니다 |
| `bash infra/manual-off.sh` | 자동 운영으로 돌아갑니다. 업무시간 밖이면 바로 Pod를 내리고 EC2를 끕니다. 업무시간이면 Pod를 두고 평소처럼 18:00/18:10에 끕니다. Pod 삭제에 실패하면 EC2를 끄지 않고 "EC2 shutdown skipped" 메일을 보냅니다 |

- 수동 모드에서는 Pod와 EC2가 계속 과금됩니다. 작업이 끝나면 반드시 `manual-off.sh`를 실행하세요.
- 서버에서 `sudo /opt/voc-llm/bin/voc-ctl.sh status`로 `mode: manual / auto`를 확인할 수 있습니다.

#### 실행 전 IP 허용 확인 (사무실 밖 PC)

보안그룹은 22번(SSH)과 443번(API)을 허용된 IP에서만 엽니다. 사무실(59.10.37.181)이 아닌 곳에서 작업하면 먼저 PC의 IP를 허용해야 합니다.

| 포트 | 필요한 경우 | 허용하지 않으면 |
|---|---|---|
| 22 | `manual-on.sh`, `manual-off.sh` 실행. 두 스크립트 모두 SSH로 서버에 명령을 보냅니다 | `manual-on.sh`가 EC2만 켜고 SSH에서 멈춥니다. Pod도 뜨지 않고 수동 모드도 켜지지 않습니다. 업무시간 밖이면 EC2를 꺼 줄 자동 종료도 없어 계속 과금됩니다. `manual-off.sh`는 서버에 닿지 못해 아무것도 끄지 못합니다 |
| 443 | 이 PC에서 curl이나 Postman으로 API를 직접 호출 | 응답 없이 시간 초과(curl 코드 `000`)가 납니다. 서버는 정상이어도 이렇게 보이니 서버 장애로 오해하지 마세요 |

스크립트 실행만 할 때는 22번만 열면 됩니다. 443번은 고객사 접속 목록과 같은 규칙이므로 꼭 필요할 때만 여세요.

```bash
# 1) 내 공인 IP 확인
curl -s https://checkip.amazonaws.com

# 2) 허용 목록에 있는지 확인
export AWS_PROFILE=voc-llm AWS_DEFAULT_REGION=ap-northeast-2
SG=$(grep -oE 'sg-[0-9a-f]+' infra/aws.out | head -1)
aws ec2 describe-security-groups --group-ids $SG \
  --query 'SecurityGroups[0].IpPermissions[?FromPort==`22` || FromPort==`443`].{port:FromPort,ip:IpRanges[].CidrIp}'

# 3) 임시 허용 (Description에 날짜를 넣어 두면 나중에 찾기 쉽습니다)
MYIP=$(curl -s https://checkip.amazonaws.com)
aws ec2 authorize-security-group-ingress --group-id $SG \
  --ip-permissions "IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges=[{CidrIp=$MYIP/32,Description=temp-manual-YYYYMMDD}]"
#    API를 직접 호출해야 하면 FromPort/ToPort를 443으로 바꿔 한 번 더 실행합니다

# 4) 작업이 끝나면 manual-off.sh 실행 뒤에 제거 (먼저 지우면 manual-off.sh가 SSH에 접속하지 못합니다)
aws ec2 revoke-security-group-ingress --group-id $SG --protocol tcp --port 22 --cidr $MYIP/32
aws ec2 revoke-security-group-ingress --group-id $SG --protocol tcp --port 443 --cidr $MYIP/32   # 443을 열었을 때만
```

- 집이나 공유기를 바꾸면 공인 IP가 달라집니다. 작업할 때마다 1)번부터 다시 확인하세요.
- 고객사 키는 `client_keys.conf`의 주석이 아닌 줄에 있습니다. 첫 줄 주석에는 `"Bearer <키>"` 예시가 들어 있습니다. 그 예시를 키로 쓰면 401이 납니다.

## 3. 배포와 운영 버튼 (GitHub Actions)

GitHub 저장소 → **Actions** → **aws_build_deploy** → **Run workflow**에서 `action`을 고르고 실행합니다.

| action | 하는 일 | 언제 쓰나 |
|---|---|---|
| `deploy` | 테스트 후 코드만 서버에 반영합니다. 실행 중인 Pod와 일시정지 상태는 그대로 둡니다 | 스크립트나 설정 템플릿을 고쳤을 때 |
| `pause` | 코드 반영, 실행 중인 Pod 종료, 일시정지를 합니다. 이후 08:30 자동 기동과 업무시간 감시가 멈춥니다 | 테스트 기간, 장기간 사용하지 않을 때 |
| `resume` | 코드 반영, 일시정지 해제, 실행 중인 Pod 종료를 합니다. **업무시간(평일 08:30~18:00)이면** 최신 설정으로 새 Pod를 띄우고, 그 외 시간이면 다음 평일 08:30에 뜹니다 | 운영 재개, 모델이나 `.env`를 바꾼 뒤 Pod를 새로 띄울 때 |

- 모든 action은 먼저 테스트를 통과해야 배포됩니다. 긴급할 때는 `skip_tests`를 체크하면 건너뜁니다.
- 실행 결과(일시정지 여부, 현재 Pod, 최근 로그 3줄)는 실행 화면의 **Summary**에 표시됩니다.
- 업무시간 밖에 `resume`을 해도 Pod를 바로 띄우지 않는 이유가 있습니다. 18:00 종료가 이미 지나서, 바로 띄우면 다음 날 18:00까지 약 22시간 과금됩니다. 업무시간 밖에 꼭 띄워야 하면 5장의 `pod-start.sh --force`를 쓰세요.
- 배포 중 nginx가 재시작되어 요청이 잠깐 끊길 수 있습니다.
- 배포 러너는 보안그룹 22번(SSH)을 자기 IP에만 잠시 열고, 끝나면 성공하든 실패하든 닫습니다.
- EC2가 꺼져 있으면(평일 18:10 이후, 주말) 워크플로가 먼저 켜고 배포합니다. 업무시간 밖이면 끝난 뒤 다시 끕니다.

### 처음 한 번: Secrets와 Variables 등록

저장소 **Settings → Secrets and variables → Actions**에 등록합니다. 값은 별도로 전달된 비밀값 묶음(7z)에 있습니다.

| 종류 | 이름 | 값 |
|---|---|---|
| Secret | `AWS_ACCESS_KEY_ID` | VOC 전용 IAM 사용자 `voc-llm-admin`의 액세스 키 ID |
| Secret | `AWS_SECRET_ACCESS_KEY` | 같은 사용자의 비밀 액세스 키 |
| Secret | `EC2_SSH_KEY` | `voc-llm-key.pem` 파일 내용 전체 |
| Variable | `EC2_HOST` | `43.200.20.252` |
| Variable | `INSTANCE_ID` | `i-0690b13503d7390c9` |
| Variable | `SG_ID` | `sg-0584ec3ea11efe10d` |
| Variable | `DOMAIN` | `43-200-20-252.sslip.io` |

배포 전에 승인을 받게 하려면 **Settings → Environments → production**에서 승인자를 지정합니다.

## 4. 상태 확인

**API로 확인** (고객사 키 필요, 허용된 IP에서만 가능)

```bash
curl -s https://43-200-20-252.sslip.io/v1/models -H "Authorization: Bearer $VOC_KEY"
```

- `200`이 나오면 Pod가 떠 있습니다. 응답의 `root`가 실제 모델입니다.
- `503`이 나오면 업무시간 외이거나, 일시정지 중이거나, Pod가 기동 중입니다.
- `401`이 나오면 키가 틀린 것입니다.

질문을 보내 보려면 `tools/voc-ask.sh` 스크립트나 Postman 데스크톱 앱을 씁니다. 사용법은 스크립트 첫 부분의 주석에 있습니다.

**서버에서 확인** (SSH)

```bash
ssh -i voc-llm-key.pem ubuntu@43.200.20.252
sudo /opt/voc-llm/bin/voc-ctl.sh status          # 일시정지 여부, 현재 Pod
sudo tail -n 20 /var/log/voc-llm/pod.log | jq -c '{event,result,ts}'
```

**AWS 콘솔** (서울 리전)

- 알람: CloudWatch → 경보 → `voc-llm-` 검색. 외부 접속 감시 알람만 us-east-1 리전에 있습니다.
- 그래프: CloudWatch → 대시보드 → `voc-llm`

## 5. 서버에서 직접 운영하기 (SSH)

GitHub Actions를 쓸 수 없을 때 같은 동작을 서버에서 직접 실행합니다.

| 명령 | 동작 |
|---|---|
| `sudo /opt/voc-llm/bin/voc-ctl.sh pause` | Actions의 `pause`와 같습니다 (코드 배포 제외) |
| `sudo /opt/voc-llm/bin/voc-ctl.sh resume` | Actions의 `resume`과 같습니다 (코드 배포 제외) |
| `sudo /opt/voc-llm/bin/pod-start.sh --force` | 시간, 공휴일, 일시정지와 관계없이 지금 Pod를 띄웁니다. 다음 18:00 종료 cron이 내립니다 |
| `sudo /opt/voc-llm/bin/pod-stop.sh` | 지금 Pod를 내립니다 |
| `sudo /opt/voc-llm/bin/voc-ctl.sh shutdown` | Pod를 내리고 감시를 끈 뒤 1분 뒤 EC2를 끕니다. 업무시간에는 동작하지 않습니다 |
| `sudo touch /opt/voc-llm/state/maintenance` | 점검 모드를 켭니다. 감시와 자동 복구만 멈추고, 08:30 기동은 그대로 합니다. 끄려면 파일을 지웁니다 |

`pause`(일시정지)와 `maintenance`(점검 모드)는 다릅니다. 며칠 이상 쓰지 않을 때는 `pause`를 쓰고, Pod를 띄운 채 잠깐 손볼 때는 `maintenance`를 씁니다.

## 6. 알림 메일

알림은 SNS 토픽 `voc-llm-alerts`로 갑니다. 서울 토픽과 us-east-1 토픽 두 곳이 있고, 받는 사람을 추가할 때는 두 토픽에 각각 구독해야 합니다.

| 제목 | 의미와 조치 |
|---|---|
| START failed: no GPU | 48GB GPU 6종 모두 재고가 없습니다(약 20분간 3회 시도). 본문에 마지막 응답이 있습니다. 업무시간이면 감시가 계속 복구를 시도합니다 |
| START failed: RunPod API error | RunPod API 호출 자체가 실패했습니다(연결 실패, 키 만료, 잔액 부족, API 변경 등). 본문의 마지막 응답을 보고 원인을 고치세요. GPU 재고 문제가 아닙니다 |
| START failed: vLLM not ready | GPU는 잡았지만 15분 안에 모델이 뜨지 않았습니다. Pod는 자동 삭제됩니다. RunPod 콘솔의 Pod 로그를 확인하세요 |
| RunPod DOWN / RunPod recovered | 업무시간 중 장애를 감지했고 자동 복구를 시작했거나 끝냈습니다 |
| RunPod recovery gave up | 그날 자동 복구를 3번 했는데 또 장애가 났습니다. 그날은 더 시도하지 않습니다. 원인을 고친 뒤 `pod-start.sh --force`를 실행하세요 |
| STOP failed: pod not deleted | Pod 삭제에 실패했습니다. **과금이 계속되므로** RunPod 콘솔에서 직접 삭제하세요 |
| EC2 shutdown skipped | 18:10에 Pod 삭제에 실패해 EC2를 끄지 않았습니다. **과금이 계속되므로** RunPod 콘솔에서 Pod를 직접 삭제하세요 |
| Holiday sync failed | 공휴일 API 갱신에 실패했습니다. 갱신될 때까지 평일은 모두 운영합니다 |
| CloudWatch `voc-llm-*` ALARM | EC2의 CPU, 메모리, 디스크, 외부 접속 등에 문제가 생겼습니다. 각 알람의 OK 메일이 오면 정상으로 돌아온 것입니다 |

## 7. 키와 설정 바꾸기

- **`.env` 값(RunPod 키, 모델 등)**: 서버의 `/opt/voc-llm/.env`를 고친 뒤 Actions에서 `resume`을 실행합니다. `VLLM_API_KEY`를 바꿨을 때는 nginx에 반영되도록 반드시 배포(`deploy` 이상)를 해야 합니다.
- **고객사 키**: 서버의 `/etc/nginx/voc-llm/client_keys.conf`에 `"Bearer <키>" 1;` 줄을 추가하거나 지운 뒤 `sudo systemctl reload nginx`를 실행합니다.
- **허용 IP(고객사, 관리자)**: EC2 → 보안 그룹 → `voc-llm` → 인바운드 규칙의 443번에 추가합니다.
- **모델 변경**: `.env`의 `MODEL_ID`를 바꾸고 `resume`을 실행합니다. 후보와 평가 결과는 [runpod-설계.md](../runpod-설계.md) 5장에 있습니다.
